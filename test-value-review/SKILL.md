# 测试价值审查

审查测试**值不值得存在**，而不是测试写得规不规范。

一条测试的价值 = 有效性 × 重要性 − 维护成本。覆盖率只证明代码被执行，不证明结果被断言；测试数量只证明数量。默认只读，审查结束后直接回复，不生成报告文件。

## 何时使用

- 审查一个 PR 里新增/修改的测试，判断能否合并。
- 审计一个模块或整个项目的单测，找出假信心和低价值检查。
- AI 生成了一批测试后，判断哪些该留、该删、该改。
- 重构前，判断哪些测试在保护行为，哪些只是在锁实现。

**不适用**：写测试、修失败测试、统计覆盖率、代码风格/lint、性能、安全、跨系统 E2E 流程编排审查（单条 Playwright/Cypress 测试的断言质量仍可审）。遇到这些，说明不在范围内，不要顺手做。

本 skill 只覆盖 **JS/TS（Jest、Vitest、Testing Library、Playwright/Cypress 测试，含组件测试）与 Python（pytest、unittest）**。其他语言的测试文件只做清单提示，不冒充已审查。

## 核心判定：四个反事实

每条结论都必须能落到一个**具体改动**或**具体缺陷**；落不到就不许下结论。

| 反事实 | 怎么做 | 结果意味着什么 | 对应问题 |
|---|---|---|---|
| **破坏** | 把被测行为改坏一行，写明改哪行 | 测试仍绿 → **FAKE 假信心** | 只测静态内容、复述实现 |
| **删除** | 删掉这条测试 | 说不出会漏哪种真实缺陷 → **WEAK 低价值** | 点击回调、弹窗开关、简单计算 |
| **重构** | 只改内部结构，不改外部行为 | 测试变红 → **BRITTLE 脆弱** | 锁私有状态、DOM 结构、调用顺序 |
| **替换** | 换掉固定输入/文案，或让实现忽略该输入 | 测试仍绿 → **没验证绑定**（UI 重点） | 只断言固定内容 |

“替换”是 UI 的专项检查。组件接收 `title`，测试只渲染 `"Alice"` 并断言 `"Alice"`——把组件改成硬编码 `"Alice"`，测试仍然绿，说明它从来没验证过 `title` 被使用。

这里的“端到端”指**穿过被测对象的公共契约**：函数走输入→输出，组件走渲染→交互→可见结果，服务走调用→持久化/返回值/事件。**不是**要求每个单测都升级成全系统 E2E；那会走向另一种过度防御。

## 判定标签、重要性与优先级

### 每条测试选一个标签

| 标签 | 定义 | 典型信号 |
|---|---|---|
| **FAKE / 假信心** | 不可能失败，或失败与行为无关 | 无断言（且不是冒烟/崩溃检查）、同义反复、mock 自证、吞错、不可达断言 |
| **WEAK / 低价值** | 能失败，但只证明框架、接线、常量、类型或内部调用 | 唯一断言是 mock 被调用、click→spy、modal 开关、getter/setter、简单算术、props 透传 |
| **BRITTLE / 脆弱** | 行为没变也会红 | 私有状态、DOM 结构、类名、整树快照、固定附带文案 |
| **STRONG / 有效** | 能捕获真实回归 | 公开契约、输入→输出、用户可见结果、期望值独立计算 |

### 重要性必须读被测代码才能判

| 级别 | 判据 | 例子 |
|---|---|---|
| **H** | 错了会有钱、权限、数据、外部契约或不可逆后果 | 支付、鉴权、定价/折扣/金额计算、订单状态机、数据迁移 |
| **M** | 普通业务规则、校验、错误分支、展示/格式化、用户可见状态 | 表单校验、空态/错误态、日期/金额展示 |
| **L** | 展示拼装、常量、getter/setter、类型或框架已保证 | 按钮 className、props 透传、`add(2,3)` |

只看测试文件只能判“有效性”，判不了“重要性”。对要判 H/M 的测试，必须读 `sources` 里的被测源码和契约；读不到就标 `UNVERIFIED`，不许猜。

### 双轴优先级

| | 重要 H/M | 不重要 L |
|---|---|---|
| **STRONG** | 保留，点名肯定 | 不报（可留可删） |
| **BRITTLE** | P2 建议处理 | P3 记录 |
| **WEAK** | P2 建议处理 | P3 记录 |
| **FAKE** | **P1 必须处理** | P2 建议删除或改写 |

**数量上限**：P1 ≤ 5 条，P2 ≤ 5 条，要加的缺口 ≤ 3 条；同一模式合并成一条，总条目 ≤ 10。超过就按“无效 × 重要”排序截断，不刷屏。

**套件结论**：可信 = 无 P1 且 P2 ≤ 1；局部假信心 = 1–2 条 P1，集中在具体模块；系统性假信心 = ≥ 3 条 P1，或深审的 H/M 测试里多数是 FAKE/WEAK。

## 工作流

### 0. 定范围

明确是：整个项目 / 某个目录 / git diff / 单个文件。没有测试就报“范围内没有可审测试”，不虚构结论。用户只给“看看测试”时，默认当前项目；项目很大时先扫全量，再按下面的策略限定深审范围。

### 1. 扫描

`<skill-base>` 是 skill 资源提示里给出的目录。把 JSON 写到系统临时目录，不要写进项目；它只是分析用的工作文件，不是交付物：

```bash
python "<skill-base>/scripts/scan_tests.py" --root .
```

PR 场景：

```bash
python "<skill-base>/scripts/scan_tests.py" --root . --changed
```

只审某个模块：

```bash
python "<skill-base>/scripts/scan_tests.py" --root . --path src/components
```

读汇总和 JSON，重点看：

- `summary`：文件数、测试数、UI 测试数、解析警告数；如果 `units=0`，到此为止。
- `top_suspects`：启发式信号排序，只是**待查清单**，不是判决。
- `parse_warnings`：扫描器解析不了的测试，必须手工读，不许假装覆盖。
- `skipped_files` / `out_of_scope_files`：说明哪些没进审查范围。
- `sources`：测试对应的被测源码，下一步读它。

### 2. 读被测代码，确定契约与后果

对要判 H/M 的测试，读 `sources` 指向的实现，回答：

1. 这条测试声称保护的行为是什么？公开契约在哪里（类型、JSDoc、README、API schema、产品文案）？
2. 如果这个行为坏了，后果是什么？钱、权限、数据、用户可见错误，还是只是样式？
3. 是否已有更强的测试覆盖同一行为（集成/E2E）？如果有，这条测试的边际价值是什么？
4. 这条测试实际执行了被测逻辑，还是把被测对象/mock 换掉了？

读不到源码、契约或调用方时，标 `UNVERIFIED`，说明缺什么；不要用“可能”“也许”凑结论。

### 3. 逐条判定

对每条进入深审的测试做四问：

1. 它断言了什么可观察结果？期望值从哪里来（手算/固定值/被测函数自己/mock）？
2. 把行为改坏一行，它会红吗？说不出具体改动，就是 FAKE 候选。
3. 只改内部结构，它会红吗？会红就是 BRITTLE 候选。
4. 删掉它，会漏哪种真实缺陷？说不出来，就是 WEAK 候选。

先假设测试是合理的，再找反证。找不到具体缺陷就判 STRONG 或 `UNVERIFIED`，不要为了产出而编造。

**大套件策略**：≤ 40 条全看；41–150 条看全部高风险模块 + 全部可疑项；> 150 条看变更/高风险模块 + 高可疑项。最终必须写明“深审 X / 总计 Y”，不许把扫描说成全审。

### 4. 需要时运行测试

运行是允许的，但只为一件事服务：**确认这条测试到底能不能失败**。

```bash
python "<skill-base>/scripts/run_test.py" --root . --file <test-file> --name "<test-name>"
```

先跑基线：绿了，说明测试当前能通过；红了，说明测试本身已经坏了。基线失败要单独报“测试已红”，不能当成“假测试”的证据。

静态判断已经足够时，不要为了“更严谨”而跑。只有运行时行为会改变结论（例如异步断言、条件分支、mock 是否真的被触发）时才跑。

**变异探测**是回答“改坏行为它会不会红”的最强证据，但会临时改源码，**必须先得到用户明确同意**。需要时直接问：

> 我可以临时把 `src/foo.ts:12` 的 `0.15` 改成 `0.05`，跑一条测试后立即恢复；可以吗？

```bash
python "<skill-base>/scripts/probe_mutation.py" --root . \
  --file <source-file> --find "<old>" --replace "<new>" \
  --test-file <test-file> --name "<test-name>"
```

- 一次只改一处、只跑一条测试。
- 选择会改变行为的改动：常量、比较符、返回值、分支、字符串、是否使用某个输入。不要改变量名、格式、注释。
- 结果：`killed` = 测试抓住了改动；`survived` = 没抓住；`baseline_failed` = 测试本来就是红的；`inconclusive` = 基线被跳过且结果无法归因。
- 脚本会备份、在 `finally` 里恢复并校验哈希。恢复失败时立即停止，报告备份路径，不要继续审。
- 用户没同意改源码，就只做静态推断，并标 `UNVERIFIED`；不要偷偷改。

### 5. 排序、合并、截断

- 先按双轴矩阵排：无效 × 重要 > 无效 × 不重要 > 脆弱 × 重要 > 低价值 × 不重要。
- 同一模式合并成一条，列出所有受影响的位置；不要一条测试写一段。
- 应用数量上限；超出时保留后果最严重的，其余在“无法判定/未展开”里说明。
- 删除重复项：同一行为已有更强测试覆盖时，指出哪条该留、哪条该删。

### 6. 直接回复

不要写报告文件、不要改测试、不要改生产代码（变异探测的临时改动除外，必须恢复）。按下面的格式直接回复。

### 7. 交付前自检

见最后一节。

## 输出格式

````markdown
## 结论

一句话：总体可信 / 局部假信心 / 系统性假信心。
范围：X 个文件 / Y 条测试；深审 A 条，扫描 B 条；证据：静态 / 运行过 N 条 / 变异验证 M 条。
最重要的一条判断：……

## 要删的

- **[P1]** `src/formatPrice.test.ts:6` `is self-consistent` — **FAKE / M**
  断言：`expect(formatPrice(1234)).toBe(formatPrice(1234))`
  存活缺陷：把格式化逻辑改成永远返回 `"$0.00"`，两边一起变，测试仍绿。
  影响：金额显示错误可以上线，测试给的是假信心。
  处理：删除；改成手算期望 `expect(formatPrice(1234)).toBe("$12.34")`。

## 要改的

- **[P2]** `src/UserCard.test.tsx:8` `renders the fixed name` — **WEAK / M**
  现在只渲染一个 `"Alice"` 并断言它；把组件里的 `{user.name}` 硬编码成 `"Alice"`，测试仍绿。
  处理：用 `"Alice"` 和 `"Bob"` 各渲染一次，断言 heading 的 accessible name 跟着变。

## 要加的

- **[P2]** `src/UserCard.tsx:12` `UserCard` 的空状态 — 现在没有测试；`user` 为空时渲染会抛错，集成层也没有覆盖。补一条组件测试即可，不要升级成 E2E。

## 不用动的

- `src/UserCard.test.tsx:13` `renders two different names` — STRONG：两个输入、两个断言，能抓住“忽略 prop”。
- 快照测试看起来可疑，但快照很小、只覆盖稳定结构，保留。

## 无法判定

- `src/bar.test.ts:44` — 依赖真实网络，静态无法判断断言是否可达；需要运行或 mock 边界后才能下结论。

## 给执行 agent 的下一步

1. 先处理 P1：删除同义反复，换成手算期望。
2. 再处理 P2：把固定内容改成两个值，断言绑定。
3. 补 1 条空状态测试；不要顺手补边界、不要改生产代码、不要更新快照。
````

硬性要求：

- 每条发现必须有 `file:line`、测试名、标签、重要性、实际断言（无断言时引用被执行的关键语句）、具体缺陷/理由、处理动作。
- P1 必须写出“改坏哪一行、测试为什么还绿”；写不出就降级或删除。
- 每条“要加的”必须说明“现在会漏哪种缺陷”，否则不许加。
- 没有发现时，直接说“没有发现需要处理的假信心/低价值测试”；有 STRONG 测试就点名 2–3 条，没有就说明整体覆盖情况。不要为了显得认真而硬凑 P3。
- 回复正文控制在 100 行左右；不要贴完整测试文件，不要逐条复述实现。

## 运行测试的规则

- 允许：跑单条测试/单个文件、确认基线；用 `run_test.py` 或项目已有的单测命令。
- 禁止：watch 模式、全量套件、覆盖率收集、`--updateSnapshot`、安装依赖、改测试配置来“让它能跑”。
- 超时默认 120 秒；超时记为 `TIMEOUT`，不要当成 killed。
- 测试跑不起来（缺依赖、环境错误）不是测试缺陷；报告“执行不可用”，继续静态审查。
- 变异探测必须得到用户明确同意；一次一处；恢复校验失败立即停止。
- 不把“跑了一次绿”当成稳定结论；明显不稳定的测试标注“可能 flaky”，不要用它证明测试有效。

## 反过度防御契约

这类模型常见的失败不是漏报，而是**怕漏报**：每条都报、每条都建议补、严重度通胀、把 mock/快照/固定文案一律判死。用下面的硬约束压住：

| 过度防御表现 | 后果 | 硬约束 |
|---|---|---|
| 每条测试都“可以更强” | 报告噪音，用户不信任 | 只报 P1/P2；STRONG 不逐条点评 |
| 建议补测试/补断言 | 测试膨胀，维护成本上升 | 禁止生成测试；要加的缺口 ≤ 3，且必须写明漏哪种缺陷 |
| 严重度通胀 | 无法排序 | P1 必须有一行存活缺陷；P1 ≤ 5 |
| 把 mock/快照/固定文案一律判死 | 误伤合理用法 | 先看契约；参考 `references/anti-patterns.md` 的例外 |
| 含糊其辞 | 无法行动 | 每条给判定 + 一行处理；不确定标 `UNVERIFIED` 并说明缺什么 |
| 逐条复述实现 | 报告冗长 | 只写“保护了什么 / 没保护什么” |
| 用覆盖率当质量 | 假指标 | 不看行覆盖率；只问“能不能失败” |
| 为凑数报 P3 | 噪音 | P3 只在“删起来很便宜、且会造成假信心”时写 |

**禁止句式**（除非后面紧跟具体缺陷）：

- “建议增加断言/提高覆盖率/补充边界测试。”
- “这个 mock 用得不好。”——mock 本身不是问题，替代了结果断言才是。
- “快照测试不好。”——小而稳定、作为补充的快照可以保留。
- “这段代码可以更优雅/更符合 AAA。”——不在范围内。
- “可能/也许会有问题。”——要么给具体缺陷，要么标 `UNVERIFIED`。

**允许的结论**：

- “这条测试没问题。”
- “这个模块整体可信，只有一条 P2。”
- “无法判定，因为缺少被测实现/运行环境。”

## 明确不报

- 命名、AAA 注释、测试文件组织、断言消息风格。
- 行覆盖率、分支覆盖率、变异分数、测试数量。
- mock 本身、snapshot 本身、固定文案本身。
- 类型系统/框架已经保证的东西（除非运行时真的会坏）。
- 不可能触发的边界（例如类型已排除的输入）。
- 测试速度、测试隔离、fixture 设计——除非它们直接导致假绿或无法失败。
- 便宜且无害的重复测试——除非它更脆弱且没有速度/定位收益。
